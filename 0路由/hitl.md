# 人机确认门（HITL）

本智能体有**两处必须停下来问用户**的地方。它们不是可选的礼貌，是流程正确性的一部分：
门① 决定了"要下哪些"，门② 决定了"怎么下"。

---

## ★门① 确认文献列表

**位置**：检索之后、构建下载队列之前（P2）

**为什么必须有**：检索是宽召回，20 条候选里用户可能只想要 5 条。未经确认就批量下载，
既浪费配额，也可能触发出版商的批量下载风控。

### Agent 应该怎么做

1. 跑 `pipeline.py run --input "<需求>"`（**不要**加 `--yes`）
2. 命令会停在门①，打印候选表（序号 / 被引 / 年份 / 标识符 / 标题）
3. **把这张表原样转述给用户**，并问要哪几条
4. 用户答复后，用 `pipeline.py resume --select 1,3,5-9` 继续

### 选择语法

| 命令 | 含义 |
|---|---|
| `resume --all` | 全部要 |
| `resume --select 1,3,5-9` | 按候选表序号勾选（支持区间） |
| `resume --select-file picks.txt` | 文件里一行一个 DOI 或序号 |
| `resume --deselect 2,4` | 先全选再排除 |
| `run ... --yes --limit-select 10` | **非交互**：自动选前 10 条并一路跑完 |

### 什么时候可以跳过门①

**只有一种情况**：用户在同一轮里已经明确给出了要下载的清单（DOI 列表、文件等）。
这时候没有"候选"需要确认，输入本身就是确认。

反例：用户说"搜一下钙钛矿稳定性并下载" —— 这是**两条指令**，
`and 下载` 不构成对某个具体列表的确认。必须过门①。

## ★无人值守模式（定时任务 / 子智能体 / 批量脚本）

**当没有人可以问的时候**，不要卡在门① 上等 —— 那不叫守规矩，叫任务失败。
用非交互开关推进：

```bash
python 0路由/scripts/pipeline.py run --input "<需求>" \
  --year-from 2019 --limit-search 60 \
  --yes --limit-select 15 --out-dir "<交付目录>"
```

| 参数 | 真实语义 |
|---|---|
| `--yes` | 跳过门① 的人机交互，**自动选中排序靠前的 N 条**（N = `--limit-select`） |
| `--limit-select N` | 自动选前 N 条 |
| `--limit-search M` | 每源取多少候选，**必须显著大于 N**（见下） |

`--yes` 只是把"谁来选"从用户换成"排序"，**不代表跳过门②**：门② 在非交互模式下
会**打印**策略/并发/输出目录（不阻塞），Agent 应当把这几行转述给用户。

### `--limit-search` 必须显著大于 `--limit-select`

这是最容易踩的坑：候选池 20 条、却要选 15 条，等于**几乎没有筛选**，
排序靠后的噪声条目必然入选。实测过 `--limit-search 20 --limit-select 15`
把「心血管疾病药物靶点预测」「人机交互认知负荷预测」这类完全跑题的文献选进了下载队列。

**建议 `--limit-search ≥ 3 × --limit-select`。** 脚本在候选池过小时会主动告警。

### 更稳的做法：多角度查询 + 人工清单

单一 `--query` 的相关性排序**不足以直接支撑 `--limit-select`**（原因见
[routing.md](routing.md) 的"相关性排序的第二个陷阱"）。无人值守下更可靠的流程：

```bash
# 1) 多个查询角度各取一批，快照落盘
python 0路由/scripts/search.py --query "角度一" --limit 40 --year-from 2019 --out pool1.json
python 0路由/scripts/search.py --query "角度二" --limit 40 --year-from 2019 --out pool2.json
# 2) 合并去重后人工（或按规则）挑选，写成清单
# 3) 用清单落地——队列里没有的条目会被自动追加
python 0路由/scripts/pipeline.py run --input picked.txt --select-file picked.txt --out-dir "<目录>"
```

`--select-file` 的语义是**以该文件为准**：先清空原有选择，再只保留文件里列出的；
文件里出现、而队列里没有的标识符会**追加**为手工条目（`origin=manual`）并自动补全元信息。
所以"我在好几批检索结果里人工挑了一批"这种最真实的用法可以直接落地。

## 多轮运行：队列是「本次任务」，不是「累计成果」

**每次 `run --input ...` 都会整体替换队列。** 这带来两个必须知道的后果：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 第二轮的元信息表只有本轮条目，但磁盘上还有上一轮下的 PDF | `finalize` 只统计队列内的条目；上一轮的 PDF 被归为"不属于本次队列"，只进 `doi_index.json` | 想要一份覆盖全部成果的表，就用**并集清单**再跑一轮（见下） |
| 上一轮的失败归因不见了 | `failures.md` 反映的是最近一次运行 | 每轮有失败项时会额外留一份 `failures-<时间戳>.md` 做审计线索 |

**要一份自洽的合并交付物**，把各轮成功项合并成清单再跑一次：

```bash
python 0路由/scripts/pipeline.py run --input union_ids.txt --select-file union_ids.txt --out-dir "<目录>"
```

这样队列与元信息表都覆盖全部条目，表里的行数与磁盘 PDF 数一致。

## ★门② 确认下载策略

**位置**：队列就绪之后、真正下载之前（P4）

**为什么必须有**：同一份清单在不同策略下结果差别很大，而且涉及合规与风控：

| 要确认的事 | 为什么问 |
|---|---|
| 灰色源是否放行 | 见 [policy.md](policy.md)——取决于司法辖区与机构授权 |
| 并发与请求间隔 | 图书馆出口 IP 是共享的，高并发可能连累整个网段 |
| 是否拉补充材料（SI） | 会显著拉长耗时 |
| 是否转 Markdown（`--md`） | 额外产物，Agent 阅读用；PDF 仍是默认交付物 |

### Agent 应该怎么做

1. `pipeline.py` 在门② 会打印当前生效的策略、并发、延迟、输出目录
2. 把这几项**转述给用户**，特别是灰色源开关
3. 用户确认后再跑 `download.py`（`pipeline.py resume` 会自动接上）

### 快速路径

`resume --racing` 强制灰色源竞速引擎（对应上游 `--scihub`）。
不指定时按 `workspace/scansci-pdf/config.json` 里的策略档位走。

## 部署关也是"门"

首次使用前还有一道：**部署关**（`bootstrap.py check/plan/apply`）。
它需要用户提供的信息（邮箱、学校、API key、是否装浏览器）不是 Agent 能自己决定的。
详见 [bootstrap.md](bootstrap.md)。

---

## 给 Agent 的提醒

- **不要替用户做这两次确认。** 门① 和门② 的默认行为是"停下来打印并等待"，
  这是刻意的设计。
- **不要为了"跑通"而用 `--yes` 绕过。** `--yes` 是给自动化脚本用的，
  在对话场景用它等于替用户拍板。
- 用户改主意很常见（"再加两篇""第 7 条不要"）。`resume` 可以反复跑：
  它每次都会重新读队列、重新构建，是幂等的。
